# 无硬件的仿真与机器人可视化路线

## 1. 结论

本项目从现在起采用 `Simulation First（仿真优先）`：完成第 1.0 版以前不要求购买或连接真实机械臂。仿真不是低配替代品，而是本项目故障注入、自动重置、批量实验、自愈验证和机器人学习的数据基础。

真实硬件只作为未来可选适配层。上层的任务规划、技能接口、诊断、恢复、回合记录和评测不得依赖某一台真实机器。

## 2. 四种工具各自解决什么问题

| 工具 | 中文定位 | 你用它观察什么 | 它不能证明什么 |
|---|---|---|---|
| `rqt_graph（ROS 2 节点关系图）` | 通信拓扑可视化 | 节点、话题、发布与订阅关系 | 不能证明机器人运动正确 |
| `RViz（机器人可视化工具）` | 状态和规划结果查看器 | 机器人模型、关节状态、坐标系、规划轨迹、图像和点云 | 不提供真实物理接触与摩擦 |
| `ros2_control mock hardware（机器人控制虚拟硬件）` | 没有电机时的控制接口替身 | 控制器加载、关节命令、状态反馈、轨迹执行链 | 不能验证真实电机、延迟和动力学 |
| `Gazebo（物理仿真器）` | 带物理和传感器的虚拟世界 | 重力、碰撞、摩擦、机械臂、夹爪、相机、深度图像 | 仍然存在仿真与现实差距 |
| `MoveIt 2（机械臂运动规划框架）` | 规划与碰撞检查 | 逆运动学、路径、碰撞场景和末端位姿 | 不代替控制器或物理世界 |
| `ManiSkill（机器人学习仿真平台）` | 批量机器人学习实验 | 环境重置、随机化、回合、轨迹和策略评测 | 不与 ROS 2/Gazebo 主线同时入门 |

要牢牢记住：RViz 是“看见状态”，Gazebo 是“模拟世界”。在 RViz 中看到机械臂移动，只证明显示的关节状态或规划轨迹发生了变化；在 Gazebo 中完成抓取，才进一步覆盖碰撞、夹爪接触和物体运动。

## 3. 为什么不从第一周就上 Gazebo

学习顺序采用逐层增加真实性的方式：

```text
ROS 2 通信
  → rqt_graph（看节点与话题）
  → RViz（看坐标、模型与规划）
  → ros2_control mock hardware（验证控制链）
  → Gazebo（加入物理、物体和传感器）
  → ManiSkill（进行批量机器人学习实验）
```

如果第 2 周直接上 Gazebo，一次失败可能来自通信、机器人描述、坐标、控制器、物理插件或显卡。分层学习能让你知道错误属于哪一层。

## 4. 16 周的仿真与可视化交付

| 周次 | 仿真或可视化工具 | 本周必须展示的画面 | 无硬件验收标准 |
|---|---|---|---|
| 1 | 终端与环境诊断 | Conda、ROS 2、显卡和软件版本报告 | 缺少串口或机械臂只显示警告，不阻塞项目 |
| 2 | `rqt_graph（节点关系图）` | 三个节点和两个话题的连接关系 | 能从关系图发现话题连接错误 |
| 3 | `RViz TF/Marker（坐标系/标记显示）` | `world→base_link→camera_link→tool0（世界→底座→相机→工具）` 坐标树 | 能制造并可视化缺失或过期坐标变换 |
| 4 | `RViz RobotModel（机器人模型显示）` 与 `joint_state_publisher_gui（关节状态图形界面）` | 拖动关节滑块，模型和坐标系同步变化 | 没有控制器和物理引擎也能验证 URDF 与关节方向 |
| 5 | `ros2_control mock_components/GenericSystem（机器人控制通用虚拟系统）` 与 RViz | 控制器接收轨迹，关节状态反馈并驱动模型 | 能说明命令接口、状态接口和控制器管理器的数据流 |
| 6 | `MoveIt 2 RViz MotionPlanning（RViz 运动规划面板）` | 拖动末端目标、显示碰撞和规划轨迹 | 规划成功与失败场景各一个，轨迹能送入虚拟控制器 |
| 7 | `Gazebo（物理仿真器）` | 桌面、机械臂、夹爪、红方块、盒子 | 一条命令启动并完成一次抓取与放置 |
| 8 | Gazebo + 技能库状态显示 | `detect/pick/place（检测/抓取/放置）` 的输入、输出和验证结果 | 技能只能通过统一接口控制仿真机器人 |
| 9 | Gazebo + Agent Trace（智能体执行轨迹） | 中文任务变成技能序列并逐步执行 | 任务规划与机器人动作在同一演示中对齐 |
| 10 | Gazebo 故障注入 | 物体移动、抓取失败或坐标错误后自动恢复 | 画面、日志和诊断证据能相互印证 |
| 11 | Headless Simulation（无界面仿真） | 自动修复前后的仿真测试结果 | 编程智能体可在无图形界面模式运行回归测试 |
| 12 | Gazebo RGB-D（彩色深度相机） + RViz Image/PointCloud（图像/点云显示） | 相机图像、深度或点云、检测框、物体坐标 | 物体坐标能从相机坐标转换到机器人底座坐标 |
| 13 | `ManiSkill（机器人学习仿真平台）` | 自动重置和 100 个实验回合的视频或轨迹 | 统计成功率、失败类型、任务时间和恢复率 |
| 14 | ManiSkill 或隔离的 Gazebo 策略评测 | 经典技能与 ACT 学习型技能对比 | 使用同一批初始场景和随机种子公平比较 |
| 15 | Dashboard（仪表盘）与回放工具 | 一条命令启动、执行、录制、评测、回放 | 干净 Conda 环境能够复现完整仿真流程 |
| 16 | GIF/Video/Benchmark（动图/视频/基准评测） | 正常抓取、自愈恢复、自然语言调度三个演示 | 招聘方无需硬件即可按说明复现核心结果 |

## 5. 第 2—7 周的具体推进顺序

### 第 2 周：先看通信图

运行发布者和订阅者后启动：

```bash
# 启动 ROS 2 节点和话题关系图
rqt_graph
```

分别截图正常连接和话题名不一致。你必须能从箭头关系说明发布者与订阅者为什么连接或断开。

### 第 3 周：用 RViz 看坐标与诊断

启动静态或动态坐标发布者，在 RViz 中增加：

- `TF（坐标变换显示）`：查看整棵坐标树。
- `Axes（坐标轴显示）`：确认方向和位置。
- `Marker（标记显示）`：显示任务目标或故障位置。
- `DiagnosticArray（诊断消息）` 可先通过命令行查看，后续再加入自定义面板。

正常场景保存一张截图；停止相机坐标发布者后再保存一张。故障记录必须解释画面变化和日志证据。

### 第 4 周：不用物理引擎也能验证机器人模型

目标是把自己的 URDF（统一机器人描述格式）加载到 `robot_state_publisher（机器人状态发布器）`，再用 `joint_state_publisher_gui（关节状态图形界面）` 手动改变关节值。

RViz 至少增加：

- `RobotModel（机器人模型显示）`。
- `TF（坐标变换显示）`。
- `Grid（参考网格）`。

验收时逐个关节拖动，检查旋转轴、上下限、父子链接、视觉模型和碰撞模型。此阶段不要求 Gazebo。

### 第 5 周：用虚拟硬件跑通控制链

URDF 中配置 `ros2_control（机器人控制框架）` 的虚拟硬件接口。使用 `mock_components/GenericSystem（通用虚拟系统）` 让命令接口直接反馈为状态接口，然后加载：

- `joint_state_broadcaster（关节状态广播器）`。
- `joint_trajectory_controller（关节轨迹控制器）`。

发送两组不同轨迹，在 RViz 观察模型运动，并用命令行查看控制器、命令接口和状态接口。这里验证的是软件控制链，不假装验证了真实电机。

### 第 6 周：MoveIt 2 与 RViz 规划

先使用 MoveIt 2 的演示或虚拟控制器：

1. 在 RViz 拖动末端执行器交互标记。
2. 规划并显示轨迹。
3. 增加碰撞物体，观察规划绕开障碍。
4. 设置不可达目标，记录规划失败。
5. 把成功轨迹送入第 5 周的虚拟控制器。

只有这一链路稳定后，才接 Gazebo。

### 第 7 周：进入 Gazebo 物理仿真

建立桌面场景，加入机械臂、夹爪、红方块和盒子。Gazebo 负责物理世界，RViz 同时用于观察坐标、规划场景和轨迹。

```text
Gazebo（物理、碰撞、传感器）
  ↕ ROS 2 bridge/plugin（机器人通信桥接或插件）
ROS 2 + ros2_control（通信与控制）
  ↕
MoveIt 2（运动规划）
  ↕
RViz（状态与规划可视化）
```

最终录制 30—60 秒视频：启动场景、检测红方块、规划、接近、闭合夹爪、抬起、移动到盒子、释放。

## 6. 推荐的机器人模型

主线建议使用 `Franka Panda（弗兰卡熊猫七自由度机械臂）` 或 MoveIt 2 教程当前提供的同类示例机器人，原因是教程、配置和演示资源完整。不要同时支持多个机器人。

选择模型后连续用到第 14 周；如果模型替换不服务当前里程碑，就不更换。你的工程价值在 Agent、技能、诊断和评测，不在收集机器人模型。

## 7. 无硬件项目仍然必须诚实说明的限制

README 和简历中应写“在 Gazebo/ManiSkill 仿真中验证”，不能写成已经部署到真实机械臂。以下问题只有真实硬件才能充分验证：

- 电机响应、控制周期抖动与网络延迟。
- 相机噪声、曝光、遮挡和标定误差。
- 摩擦、柔性、回差、夹爪力与物体材质。
- 紧急停止、限位、碰撞安全与设备断连。

这不会削弱项目。相反，明确仿真假设、加入随机化与延迟、记录已知差距，会体现工程判断力。

## 8. 如何减少仿真与现实差距

从第 7 周开始逐步加入：

- 物体位置、质量、摩擦和颜色随机化。
- 相机噪声、深度缺失和检测延迟。
- 控制命令延迟、关节状态噪声和偶发超时。
- 抓取位置偏差和物体在接触后移动。
- 固定随机种子，确保问题可复现。

先建立一个确定性成功场景，再每次只增加一种扰动。不要在基线尚未成功时同时随机化所有因素。

## 9. 每周必须保存的视觉证据

```text
assets/demos/week_XX/（第 XX 周演示素材目录）
├── normal.png                    # 正常状态截图
├── failure.png                   # 故障状态截图
├── demo.mp4                      # 关键流程短视频
└── README.md                     # 场景、命令、版本与观察结论
```

不要从第一天创建全部空目录；完成当周功能时再创建对应目录。视频中同时显示仿真或 RViz 画面与关键日志，确保动作和系统证据能够对齐。

## 10. 真实硬件何时再考虑

只有满足以下条件后才值得接真实硬件：

1. Gazebo 中的抓取与放置可以重复运行。
2. 技能接口不依赖仿真专用对象。
3. 控制器、坐标系和安全限制已经文档化。
4. 故障恢复有最大重试次数和安全停止。
5. 自动测试可以在无界面仿真中运行。

届时只新增 `hardware adapter（硬件适配器）` 和设备配置，不重写 Agent、技能库或评测系统。
