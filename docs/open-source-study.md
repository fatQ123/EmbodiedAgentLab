# 开源项目学习手册

## 1. 学习目标

学习开源项目不是从第一行读到最后一行，也不是把示例复制进自己的仓库。每次阅读只解决一个当前问题，并完成下面的闭环：

```text
提出问题
  → 找到最小示例
  → 跑通原版
  → 画出调用链
  → 改一个行为
  → 故意制造故障
  → 用日志定位
  → 脱离原项目重写最小版本
  → 接入 EmbodiedAgentLab（具身智能体实验室）
```

完成一次闭环后，你应该能回答三件事：它解决什么问题、数据怎样流动、失败时从哪里开始查。只能复述项目说明但不能修改和调试，不算学会。

## 2. 一次开源项目学习的七个步骤

### 第一步：先写问题，不先下载代码

用一句中文写清本次目的。例如：“我想知道 ROS 2（机器人操作系统第二代）的发布者怎样创建消息并发送到话题。”范围必须小到能在 2—4 小时内验证。

不要写“本周学完 MoveIt 2（运动规划框架）”。应写“找到位姿目标进入规划器的入口，并修改目标位姿后重新运行”。

### 第二步：做 20 分钟仓库侦察

只看以下内容：

1. `README（项目说明）`：项目解决的问题、支持的版本、最小运行方式。
2. `LICENSE（开源许可证）`：是否允许复制和修改，引用时需要保留什么。
3. `package.xml/pyproject.toml/CMakeLists.txt（依赖与构建配置）`：依赖、软件包名、可执行程序入口。
4. `examples/tutorials/demos（示例/教程/演示目录）`：选择最小示例。
5. `test（测试目录）`：作者认为什么行为最重要。
6. `issues（任务与缺陷记录）`：只搜索你遇到的具体错误，不漫游阅读。

把当前提交编号保存到笔记，避免几周后上游变化而无法复现：

```bash
# 显示当前开源仓库的提交编号
git rev-parse HEAD

# 查看最近十条提交，理解项目近期修改方向
git log --oneline -10
```

### 第三步：先运行最小示例

只运行一个示例，不一次启动整套系统。记录操作系统、ROS 2 发行版、Conda 环境、依赖版本、完整命令、预期输出和实际输出。

```bash
# 建议把外部项目放在主仓库之外，避免把第三方代码误提交
mkdir -p ../open-source-labs

# 只获取当前分支的最新历史，减少首次下载量
git clone --depth 1 开源仓库地址 ../open-source-labs/项目名

# 进入开源项目并记录提交编号
cd ../open-source-labs/项目名
git rev-parse HEAD
```

首次学习不要立刻 `fork（派生仓库）`。只有准备向上游提交修复时再派生；普通阅读和实验使用本地克隆即可。

### 第四步：建立“入口—数据—出口”调用链

先找启动入口和配置，再跟踪一条主路径，不跟踪所有分支。常用搜索方法：

```bash
# 列出文件，快速认识目录结构
rg --files | sed -n '1,120p'

# 搜索可执行入口、节点类或关键函数
rg "main\(|create_node|Node\(" .

# 搜索参数名、话题名或错误代码在何处产生和消费
rg "参数名或话题名或错误代码" .

# 查看一个文件最近为什么这样修改
git log -p -- 路径/文件名

# 查看某一行最后由哪次提交修改
git blame 路径/文件名
```

每次只画一条调用链，例如：

```text
launch（启动文件）
  → node（节点构造函数）
  → parameter（参数读取）
  → callback（回调函数）
  → publisher（发布者）
  → topic message（话题消息）
```

### 第五步：完成“三改一坏”

对每个最小示例完成四个实验：

1. 改名字：修改节点名、话题名、参数名或技能名。
2. 改行为：修改发布频率、目标位姿、超时或重试次数。
3. 加观测：增加中文日志、状态输出或测试断言。
4. 改坏它：制造配置错误、超时、坐标缺失或接口不匹配，再用工具定位。

如果只是原样跑通，你证明的是安装能力；完成“三改一坏”，才开始证明理解能力。

### 第六步：关掉参考项目，自己重写

不要复制整个目录。关闭参考代码后，用自己的命名和结构写一个最小版本；遇到卡点再回去查看。只迁移当前主项目真正需要的接口。

若确实复制了代码或配置，必须在文件或文档中注明来源仓库、文件路径、提交编号与许可证。不要复制不理解的辅助层，也不要删除原作者版权信息。

### 第七步：形成四份证据

每次开源学习至少留下：

1. 一张“调用链图”或一段中文数据流说明。
2. 一个能运行的最小实验。
3. 一篇故障记录，包含现象、证据、根因、修复和回归测试。
4. 一个接入主项目的独立提交；提交说明写明“借鉴了什么设计”，而不是声称原创上游代码。

## 3. 开源阅读卡模板

每次阅读在 `docs/notes（学习笔记目录，功能出现时再创建）` 建一张卡片：

```markdown
# 项目名与本次问题

## 固定版本
- 仓库：填写上游地址
- 提交：填写完整提交编号
- 许可证：填写许可证名称

## 我想回答的问题
用一句中文描述本次问题。

## 最小运行命令
写出带中文注释的命令和预期输出。

## 调用链
从启动入口写到最终输出，最多十步。

## 三改一坏
- 改名字：记录变化和结果。
- 改行为：记录变化和结果。
- 加观测：记录新增日志或断言。
- 改坏它：记录现象、证据、根因和修复。

## 迁移到主项目
说明只借鉴了什么接口、结构或思路，以及没有复制什么。

## 仍未理解
列出最多三个具体问题，作为下一次阅读入口。
```

其中 `Markdown（轻量级文档格式）` 模板里的英文标题或代码词都已经在中文上下文中解释；实际笔记继续采用同一原则。

## 4. 16 周开源项目学习地图

每周只设置一个“主读仓库”。其他仓库只能作为查错资料，不能同时开新学习主线。

| 周次 | 主读开源项目 | 只读范围 | 必须完成的修改 | 迁移到主项目的成果 |
|---|---|---|---|---|
| 1 | 当前自己的仓库 | 项目配置、入口、测试 | 给诊断工具增加一项检查并写测试 | 熟悉安装、测试、分支与提交 |
| 2 | [ros2/examples（ROS 2 官方示例）](https://github.com/ros2/examples) | `rclpy（ROS 2 的 Python 客户端库）` 中最小发布、订阅、服务示例 | 改话题名、频率、日志；制造名称不一致 | 三节点通信系统 |
| 3 | [ros2/examples（ROS 2 官方示例）](https://github.com/ros2/examples) | 动作接口与生命周期相关最小示例 | 制造动作终止、服务超时和节点退出 | 长任务与诊断用例 |
| 4 | [ros2/examples（ROS 2 官方示例）](https://github.com/ros2/examples) | 对照同一功能的 `rclpy/rclcpp（Python/C++ 客户端库）` | 把自己的一个 Python 节点重写为 C++ | 语言对照笔记与 C++ 节点 |
| 5 | [ros2_control_demos（机器人控制官方演示）](https://github.com/ros-controls/ros2_control_demos) | `Example 7（示例 7）` 的描述、硬件接口、控制器和启动文件 | 改一个关节限制；制造控制器未启动 | 轨迹到关节的数据流与控制配置 |
| 6 | [moveit2_tutorials（MoveIt 2 官方教程）](https://github.com/moveit/moveit2_tutorials) | 运动规划接口、规划场景、笛卡尔路径 | 改位姿目标、加入障碍、制造无解目标 | `move_to_pose（移动到位姿）` 技能 |
| 7 | [ros_gz_project_template（Gazebo 与 ROS 2 官方项目模板）](https://github.com/gazebosim/ros_gz_project_template) | `description/bringup/application/worlds（描述/启动/应用/世界目录）` | 增加一个模型和启动参数；停止一个桥接节点 | 正规仿真目录与抓放演示 |
| 8 | 自己的技能库 | 接口、结果对象、测试 | 给技能增加验证、超时和回滚 | 稳定技能契约，不引入新框架 |
| 9 | [langgraph（状态图智能体框架）](https://github.com/langchain-ai/langgraph) | 最小工具循环与状态传递示例 | 增加失败分支、最大循环次数与超时 | 先手写循环，再对照重构状态图 |
| 10 | 自己的诊断与恢复代码 | 错误分类、证据收集、恢复策略 | 新增一种可复现故障及回归测试 | 自愈闭环，避免被框架代码淹没 |
| 11 | 自己的编程智能体 | Git 差异、测试执行、进程限制 | 故意设置重试缺陷并自动修复 | 受限沙箱与分支修复演示 |
| 12 | `OpenCV/PyTorch（视觉库/深度学习框架）` 官方最小教程 | 图像读取、张量、推理模式 | 改输入尺寸、设备与阈值；制造维度错误 | 图像到物体位姿的最小管线 |
| 13 | [ManiSkill（机器人学习与仿真平台）](https://github.com/mani-skill/ManiSkill) | 一个环境的重置、观察、动作、步进与评测 | 改随机种子与物体位置，运行十回合再扩到百回合 | 实验回合记录器与指标 |
| 14 | [LeRobot（机器人学习框架）](https://github.com/huggingface/lerobot) | 数据集格式、ACT 策略训练和评测入口 | 先用小数据过拟合验证管线，再做正式训练 | `act_pick（ACT 学习型抓取）` 技能 |
| 15 | 自己的完整仓库 | 命令行入口、安装、端到端测试 | 在干净 Conda 环境复现一次 | 一条命令运行完整系统 |
| 16 | 上述笔记与提交历史 | 许可证、引用、演示、已知限制 | 删除无用试验代码，补引用与复现信息 | 可投递的第 1.0 版作品 |

## 5. 每周时间分配

以每周 15—20 小时为例：

- 2 小时：阅读项目说明、配置、最小示例和许可证。
- 3 小时：严格按上游说明跑通最小示例。
- 3 小时：画调用链，并用搜索工具确认每个节点。
- 3 小时：完成“三改一坏”和故障定位。
- 5 小时：关闭参考项目，在主仓库独立实现。
- 2 小时：测试、学习卡、故障记录、演示和提交。

如果上游示例 3 小时仍未跑通，停止继续安装新依赖。先固定错误信息、环境版本和最小复现，再查官方任务记录；不要用连续更换教程的方式绕过问题。

## 6. 如何判断该读源码还是先用接口

优先读接口和示例：当你还不能跑通最小功能，或只是需要调用某项能力时。只有在以下情况进入实现源码：

- 文档没有解释关键行为。
- 日志显示错误来自框架内部。
- 你需要扩展一个明确接口。
- 你需要理解性能、线程、生命周期或恢复边界。

进入源码后仍然只追踪一条调用链。看到不相关的抽象层，先记录名称，不横向展开。

## 7. 常见无效学习方式

- 从仓库第一个目录顺序读到最后一个目录。
- 同时克隆十几个类似项目，没有任何一个形成实验。
- 复制完整示例后只修改名称。
- 遇到错误立刻换教程，未保留错误和环境信息。
- 阅读架构文章却不跟踪真实入口和数据流。
- 把第三方源码直接放入主仓库，却不记录许可证和来源。
- 只做成功演示，不制造故障和写回归测试。

## 8. 第一次开源学习任务

第 2 周开始前，先用 `ros2/examples（ROS 2 官方示例）` 做一次完整演练：

1. 固定与你的 ROS 2 Jazzy（机器人操作系统第二代 Jazzy 发行版）匹配的分支或标签，并记录提交编号。
2. 跑通一个 Python 发布者和订阅者。
3. 画出“节点启动→创建发布者→定时回调→构造消息→发布→订阅回调”的链路。
4. 把话题名和发布频率改成参数。
5. 增加中文日志。
6. 故意让两端话题名不同，使用 ROS 2 命令行定位。
7. 关闭参考代码，在自己的 `ros2_ws（ROS 2 工作空间）` 重写。
8. 为参数和消息行为增加测试，再形成独立提交。

这次演练完成后，以同样模板学习后面的机器人控制、运动规划、仿真、智能体和机器人学习项目。
